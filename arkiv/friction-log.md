# Friction log (raw notes while building; distilled into friction.md)

- 2026-10-11 · SDK 0.8.1 · README install snippet shows `"@arkiv-network/sdk": "^0.6.0"` while npm installs 0.8.1, and the docs home says "SDK v0.6.0"; Python guide says v0.4.4. Expected one version across docs. Fix: generate the version string from the package.
- 2026-10-11 · `publicClient.select(...).limit(3).fetch()` with no `where` throws "A query needs at least one filter — the language has no spelling for 'match every entity'". Expected: either allowed with a limit, or documented up front. Workaround: every entity carries `app = "switched-off"` and every query starts with `eq("app", ...)`.
- 2026-10-11 · Faucet (hub.arkiv.network/faucet) needs a browser wallet connection + sign-in; no "paste an address" path. A server-generated project key can't be funded directly; had to claim to a personal wallet and transfer. Fix: allow address-only claims with a captcha.
- 2026-10-11 · Tiramisu docs page lists no fee model, no block time, no max expiry, no payload/attribute limits (only constant names in the sidebar). Measured: create cost 97,160 gas × 1 gwei ≈ 0.0000972 GLM, identical for 1-day, 30-day and 365-day expiry; block time 2 s (getBlockTiming). Expected: docs say whether lifetime is priced.
- 2026-10-11 · `ExpiryExtended` event carries the owner, not the extender; with `permissionlessExtension` the only way to know who kept an entity alive is fetching each tx's `from`. Documented in the type comment (good), but costs one extra RPC per event for a "confirmations" count.
- 2026-10-11 · createEntity round trip 7.3–9.8 s (send + receipt) from India over public RPC.
- 2026-10-11 · Expiry works exactly as documented: an entity created with `ExpirationTime.fromSeconds(40)` at block 435522 was gone from `select(...)` and `getEntity` by block 435558, while `select(...).atBlock(435522n)` still returned it. Smooth, and it is what our "rewind the register" view is built on. Not documented: how far back nodes keep queryable history (we queried block 1000 without error but cannot tell "pruned" from "empty").
- 2026-10-11 · `getEntity` on an expired key throws "No live entity with key … It was never created, or it has been deleted or" (expired). One error for three cases; an `expired` flag (or the expiry block) would let apps say "lapsed at 14:02" instead of "not found".
- 2026-10-11 · No `orderBy` on the query builder and `MAX_LIMIT = 200`: lists are sorted client-side after walking pages.
- 2026-10-11 · Raw JSON-RPC: `arkiv_query` with `app = "switched-off"` (double-quoted string) fails `{"code":-32001,"message":"unexpected character","data":{"position":6}}`. The SDK renders `app = str('switched-off') AND type = str('registrar')`. The grammar IS documented (docs.arkiv.network/json-rpc/querying-data/), but the Tiramisu network page that lists the RPC URL doesn't link to it, and the parse error gives only a position. We first found the syntax via `SelectQueryBuilder.toString()`. Fix: link the grammar from the network page, and say "expected a typed literal like str('…')" in the error.
- 2026-10-11 · `arkiv_query` returns `expiresAt` as hex block (`0xf73e6a`), attributes as `[{name,type,value}]` with u64 values as… (see schema.md). Fine for SDK users; raw-RPC users need the select object spelled out in full (all keys) — partial selects work, which is good.
- 2026-10-11 · Public RPC rate limit is 600 requests / 60 s per IP (`RateLimit: limit=600, remaining=…, reset=…`), and responses carry undocumented `Arkiv-Cost: 100` (per `arkiv_query`, regardless of select size) and an exposed-but-absent `Arkiv-Quota-Used-Percent`. Our first build hit HTTP 429 within a minute: `watchEntityEvents` polls every half block (1 s) by default, and we re-queried on every `EntityCreated` on the whole chain (other teams write constantly). An entity-creation write then failed with 429 mid-flow. Expected: limits documented on the network page, a filter on `watchEntityEvents` (e.g. by attribute or creator) so apps don't have to hear every entity on the chain, and 429s carrying `Retry-After`. Workaround: `pollingInterval: 3000` and throttled re-reads.
- 2026-10-11 · `ExpirationTime.fromSeconds(299)` throws `InvalidExpiryError: a lifetime must be a multiple of the 2s block time, got 299, which is 149.5 blocks. Try 298 or 300, or ExpirationTime.fromBlocks(n).` Excellent error (names the fix). Surprising rule though: a computed "until this moment" lifetime is almost never even. Our UI swallowed it as a generic failure the first time, so the drill's first order silently didn't land. Fix suggestion: round to the nearest block by default (or offer `fromSeconds(n, { round: 'up' })`) — we now convert every duration with `fromBlocks(ceil(s / 2))`.
- 2026-10-11 · **SDK and node disagree on attribute names.** SDK 0.8.1 validates names with `/^[A-Za-z][A-Za-z0-9._-]*$/` (src/attr/names.ts:13), so `orderId` passes client-side. The node then fails the batch: `EntityMutationError: Transaction failed: an attribute name holds "I" (0x49) at byte 5, which is outside the name charset ("A"-"Z", "a"-"z", "0"-"9", ".", "-" and "_", with a letter first)`. The message lists A-Z as allowed while rejecting a capital I. Repro: `createEntity({ attributes: { orderId: 'x' }, ... })` on Tiramisu, block ~436k. Expected: the SDK rejects it before sending (no gas spent), and the node's message matches its actual rule (lowercase only?). Workaround: snake_case names (`order_id`).
- 2026-10-11 · **SDK refuses what the RPC allows.** `select().fetch()` with no `where` throws "the language has no spelling for 'match every entity'", but the JSON-RPC docs list `*` as a valid query that matches everything. Expected: the SDK exposes `where('*')`/`all()`, or the docs say the SDK forbids it on purpose.
- 2026-10-11 · **Anonymous query budget exhausted during development** (~1 hour of a dev page polling): `{"error":"ANON_COST_LIMITED","message":"unauthenticated query budget exhausted; get an API key at https://hub.arkiv.network for a monthly quota"}`. Good message. Not documented anywhere we could find: the size of the anonymous budget, its window, and that each `arkiv_query` costs 100 units (`Arkiv-Cost` header) — so we couldn't plan for it. The access-keys page says keys in browser code can be read and spent by anyone, so a public web app either puts every visitor on the anonymous budget or runs a proxy. We run a small allowlisted proxy with a short cache, plus a "direct" switch so readers can bypass us.
- 2026-10-12 · **The relay's key ran out of its month.** Every keyed `arkiv_query` answered HTTP 429 `{"error":"QUOTA_EXCEEDED","message":"quota exhausted"}` with `arkiv-quota-used-percent: 100`; the site showed "RPC Request failed." and nothing else, because the body has no JSON-RPC `error.message`. The Hub showed no usage. Topped up on the same key: the header then read 51. (friction.md #12)
- 2026-10-12 · A relay-side upstream `fetch failed` surfaced as "Arkiv didn't answer just now (RPC Request failed. URL: … Request body: )": the banner showed the head of viem's `message`, never `details`. (friction.md #11)
- 2026-10-18 · **Page two refused.** The archive passed 200 registrar records after the day's new orders and corrections; `scripts/snapshot.ts` threw `QueryError: Query rejected (cursor, -32005): Request exceeds defined limit.`, `data.message` "cursor belongs to a different query, block or select — start a new page-through". Raw RPC: page two with the cursor alone is refused; the same request plus `atBlock: <page one's blockNumber>` answers. First fix pinned every read two blocks back; the e2e run then showed a drill order missing from its own filer's view, so page one now reads at the head and only a second page restarts pinned. (friction.md #13)
